# Hotel Agent OS 业务闭环与 Agent 化演进计划白皮书

版本：v2.0（替代 v1.0）　编制日期：2026-09-19
本版策略：不接入真实设备，业务闭环优先；先形成闭环，再逐步演进为 AI 原生 Agent。

---

## 0. 本版调整说明

v1.0 是生产化导向，把「终端信任边界」和「真实硬件接入」排在主线最前。本版按新策略重排：

| 项目 | v1.0 位置 | v2.0 位置 |
| --- | --- | --- |
| 真实读卡器 / 发卡机 / 门锁 / 公安 / 支付通道 | 阶段 2 主线 | 移入附录 A「暂缓项」 |
| 设备认证与信任边界 | 阶段 1 主线 | 移入附录 A |
| 合规与法务 | 阶段 4 主线 | 移入附录 A |
| 业务闭环（订单→入住→在住→离店→账务→房态回归） | 隐含在阶段 3 | **提升为主线 A** |
| AI 控制面与 Agent 化 | 阶段 3/5 | **提升为主线 B** |

调整理由：闭环未形成时，Agent 没有可操作的动作空间；硬件未接入时，业务闭环依然可以用模拟器完整验证。先把「AI 能否把一家酒店的业务跑起来」证明完，再谈物理世界。

## 2. 闭环定义

业务闭环的判据是两个「闭上」同时成立：

```
        ① 房闭上                                  ① 房闭上
   可售房态 VACANT_CLEAN ←──────────────  清洁 → VACANT_DIRTY
          │                                        ↑
          ↓                                        │
   预订 / 现场办理 ──→ 入住确认 OCCUPIED ──→ 离店退房
          │                     │                  │
          ↓                     ↓                  ↓
    订单 PAID            在住服务闭环        ② 钱闭上
   预订 CONFIRMED    续住/换房/报修/        账单核对 → 消费结算
   stay IN_HOUSE    客房服务/升房          → 押金退还或补收
          │                     │                  │
          └─────────────────────┴──────────────────┘
                                ↓
                    账务过账 folio CLOSED
                    ledger_entries 只追加
```

- **钱闭上**：押金 → 在住消费 → 结算 → 退款或补收，且每笔都有不可篡改的分录。
- **房闭上**：占用 → 脏房 → 清洁 → 可售，且每次房态变更都有流水。

任一条没闭上，系统就只是「入住机」而不是「酒店系统」。

## 3. 两条主线

| 主线 | 目标 | 依赖 |
| --- | --- | --- |
| A 业务闭环 | 用模拟器把一家酒店的业务全程跑通并自洽 | 无 |
| B Agent 化 | 让 AI 成为这条闭环的主要操作者 | 依赖 A 提供动作空间 |

原则：**A 先于 B，且 B 的每一步都必须立即接入 A 的动作空间**。不允许出现「AI 能力已就绪但业务动作不存在」或「业务动作存在但 AI 不在环上」。

## 4. 主线 A：业务闭环

### A0　起点固化（1 周）

| 项 | 内容 |
| --- | --- |
| 工作包 | 提交 20+ 个未跟踪文件（`lib/orders-core.ts`、`lib/hotel-core.ts`、`lib/ai-control.ts`、13 个迁移、多份文档）；把 orders 三件套接入 CI；补 `test` 聚合脚本 |
| 退出门槛 | 工作区干净无未跟踪业务文件；CI 自动跑 `test:orders` / `test:orders-d1` / `test:orders-concurrency` |

> 当前这些文件全部处于未提交状态，是最大的单点风险。

### A1　统一编排内核（2 周）

| 项 | 内容 |
| --- | --- |
| 决策 | 以 `workflow_runs` / `workflow_steps`（`lib/workflow-engine.ts`）为**唯一执行层**，`checkin_cases` 迁入，`demo_orders` 降为只读投影 |
| 工作包 | 顾客入住主流程从 `demo_orders` 迁到正式表（`orders` / `reservations` / `rooms` / `stays`）；`checkin_cases` 状态映射进 `workflow_steps`；向 `hotel-core.ts` 补 `STAY_STATUS` → `FOLIO_STATUS` 转移表 |
| 退出门槛 | 入住全链路无 `demo_orders` 写入；`workflow_steps` 可按 case 回放完整阶段；`demo_orders` 仅由投影回填 |

> 这是 A 主线唯一的架构决策点。两套状态机并行（客人走 `checkin_cases`、管理员走 `workflow_runs`）如果不收敛，后面每加一个业务动作都要写两遍。

### A2　离店与账务闭环（3 周）

| 项 | 内容 |
| --- | --- |
| 工作包 | 启用 `folios`（`open → settling → closed` 生命周期）与 `ledger_entries`（只追加，退款为反向分录）；退房报价（房费 + 在住消费 + 押金）；结算与押金退还/补收；发票开具；退房后房态 `OCCUPIED → VACANT_DIRTY` 并写 `room_status_logs`；清洁完成 `→ VACANT_CLEAN` |
| 退出门槛 | 一笔订单可从入住跑到房态回可售；账实相符（`folios.balance` 与 `ledger_entries` 合计一致）；重复结算/重复退款被幂等拦截；并发退房只成功一次；以上均有跑真实 D1 的集成测试 |

> 这是整个计划里业务价值最高的一个阶段——它把系统从「入住机」变成「酒店系统」。

**进展（2026-09-19）**：账务与离店已落地，并已接进自助终端。`lib/settlement-core.ts` + `lib/checkout-core.ts` 跑通开账、在住挂账、退房报价、结算、押金退还（反向分录）、离店、房态转脏与清洁闭环；`app/api/demo/[action]/route.ts` 新增 `checkout-lookup`（只读报价）与 `checkout-confirm`（房态与账务分开写，结算失败返回 202 `needs_followup` 转前台）；`app/page.tsx` 首屏改为「办理入住 / 办理退房」两个入口。退出门槛中「账实相符」「重复结算/重复退款被幂等拦截」「并发退房只推进一次」「一笔订单从入住跑到房态回可售」均已由真实 D1 用例覆盖（结算 35 项、并发 22 项、入住到退房闭环 25 项，见 `scripts/test-checkin-checkout-loop.mjs`）。**未完成**：发票开具、`payments` 正式化、把 A2 动作注册进 `workflow_runs` 供 AI 调用。详见 `docs/settlement-folio.md`。

> 闭环用例上线即查出一个真 bug：`findInHouseStaysWith` 把 D1 返回的下划线字段当驼峰字段用（`stayId` / `guestNameMasked` 全是 `undefined`），终端退房会一路撞到 `invalid_stay_id`。已改为显式行映射，并由该用例锁死。

> 顺带修掉一个 A0 尾巴：新增 `scripts/test-schema-drift.mjs` 与 `pnpm db:audit`，前者证明 20 张运行时 DDL 表与 5 个补列都被迁移覆盖，后者查出本地库缺 `orders` 表与 `admin_audit_events.action_id` 列——根因是没有任何环节执行迁移，本地库靠运行时 bootstrap 长出来。`action_id` 是活 bug，已按守护式补列范式修复。

## 7. 质量策略

`lib/orders-core.ts` 的双端口模式（同一逻辑跑 D1 与 node:sqlite，共享场景文件）是本仓库目前最好的工程实践，应当成为后续所有业务模块的标准：

| 做法 | 应用范围 |
| --- | --- |
| 业务逻辑与数据库解耦（端口注入） | 账务、房态、在住服务全部照此办理 |
| 共享场景文件 + 双运行器 | 新增业务的并发与幂等验收 |
| 真实 D1 绑定测试（miniflare） | 每个阶段的退出门槛 |

同时必须处理存量问题：

1. **替换自证脚本。** `scripts/test-cases.mjs` 的硬编码 `replay()`、`test-concurrency.mjs`、`test-hardening.mjs` 的本地假模型必须替换为真实调用，否则 CI 绿灯没有意义。
2. **`app/page.tsx` 拆分。** 2158 行单文件、123 个 hook，在 A2/A3 会继续膨胀，建议在 A2 前先拆出至少「自助终端」「管理后台」两个路由。
3. **发布门禁。** PR 需通过类型检查、lint、业务集成测试、密钥扫描、构建。

## 8. 三项「便宜的保险」

硬件虽然后置，但以下三件事现在做成本极低、以后返工成本极高，建议立即生效：

1. **不再新增 `demo_orders` 写入。** 它只能作为投影目标，新业务一律写正式表。
2. **不再新增「客户端声明事实」的接口。** 现有 `/api/demo/[action]` 中由客户端驱动特权状态转移的模式不再复制；新业务的状态转移走服务端。这样将来补设备信任边界时改动面是收敛的。
3. **每次 AI 决策都落 `ai_*`。** B1 之前产生的新工具若不留痕，之后需要回补历史数据。

## 结论

本仓库的护栏部分（状态机、幂等、权限、审计、脱敏）质量较高且难以速成，是真正的资产；订单领域的双端口设计与真实 D1 测试更说明团队已经找到了正确的工程做法。当前缺的不是能力，而是**闭环的完整性**与**AI 在环上的覆盖度**。

建议按本计划推进：先花 1 周固化起点，再用 9 周把业务闭环跑通，然后用 9 周把 AI 从语音前台推进为闭环的操作者。硬件与合规在闭环验证之后再启动。
