# 第二阶段产品立项及研发任务书：AI 原生 PMS

## 1. 文档信息

- 产品名称：AI Native PMS / AI 原生酒店管理系统
- 阶段：Phase 2，自有酒店核心业务系统
- 文档用途：产品立项、领域边界确认、研发拆解和生产验收
- 前置条件：第一阶段已在真实门店验证连接器、公安登记、设备工作流和人工接管

## 2. 产品定位

第二阶段逐步把订单、预订、房态、入住、账务、支付、房务和夜审迁移到自有内核。AI 成为主要操作入口，但业务内核保持确定性。

```text
客人 / 员工 / 老板 / 外部事件
              |
       AI Router 与领域 Agent
              |
        受控业务工具层
              |
        AI 原生 PMS 内核
              |
订单、预订、房态、入住、账务、房务、设备、合规
              |
     OTA / 支付 / 门锁 / 公安 / 发票
```

产品目标是让酒店拥有自己的业务事实和经营数据，同时保留连接传统 PMS 的能力，以支持存量客户和迁移期双轨运行。

## 3. 建设目标

### 3.1 产品目标

1. 自有 PMS 成为订单、预订、房态、入住、账务和房务的单一事实来源。
2. AI 可以安全完成查询、预订、入住、房务、经营分析和异常解释。
3. 支持无人入住、少人值守、多门店和远程运营。
4. 支持中国大陆门店的身份核验、公安旅业登记、支付、发票和本地设备。
5. 将第一阶段连接器继续用于 OTA、设备、公安、支付及存量 PMS 迁移。

### 3.2 工程目标

- 按 `tenant_id + hotel_id` 强制隔离数据。
- 金额统一使用最小货币单位整数，禁止浮点计算。
- 所有写操作使用状态机、幂等键、版本条件和审计。
- 关键工作流可以暂停、恢复、查询、重试和人工接管。
- 模型不可用时，预订、入住、支付、公安、门锁和夜审仍可按确定性程序运行。

## 4. 产品原则

1. AI 负责意图、计划、说明和建议，不直接写数据库。
2. 业务服务负责规则、金额、房态、权限和状态变化。
3. 公安、支付、发票和门锁的外部回执构成业务事实的一部分。
4. 页面只是业务投影，刷新或重启不能改变流程真实状态。
5. 每一个自动化动作都必须能回答：谁发起、依据什么、执行了什么、结果是什么、能否撤销。

## 5. 领域范围

### 5.1 主数据

- 集团、租户、门店、建筑、楼层
- 房型、房间、床型、设施和服务
- 渠道、价格计划、取消政策、税费规则
- 员工、岗位、角色、数据范围和审批规则
- 设备、公安终端、PMS/OTA 映射和外部编码

### 5.2 商业订单

- 订单、订单项、价格快照、优惠、渠道佣金
- 现场订单、官网直订、OTA 订单、团队和协议客户
- 取消、改期、拆单、并单、加购和退款申请

### 5.3 住宿预订

- 住宿日期、房型需求、人数、同住人和到店时间
- 一单多房、多订单共享账本、团队房和连住
- 订单商业状态与住宿状态分离

### 5.4 房态与库存

- 可售干净、可售待检查、待清扫、已锁房、在住、维修和停用
- 房型库存、实体房分配、超售限额和锁房有效期
- 版本号和并发占用控制

### 5.5 入住与身份

- 预入住、身份核验、同住人、公安登记、分房、门锁凭证
- 自助入住、人工入住、特殊证件和人工接管
- 入住记录与商业订单解耦

### 5.6 账务与支付

- Folio、账务流水、房费、服务费、税费、押金和预授权
- 分账、转账、挂账、公司账、团队账和冲销
- 支付、退款、回调、查询、对账和差错处理
- 夜审、日结、交班和锁账

### 5.7 房务与维修

- 清扫、检查、维修、失物、布草和消耗品
- SLA、优先级、任务接单、执行证据和质量复核
- 退房、换房、维修和房态之间的自动联动

### 5.8 渠道与收益

- OTA 订单、库存、价格、限制和消息
- 官网直订、优惠码和会员价
- 渠道成本、净收入、取消率和客群质量
- AI 调价建议、规则校验、审批和发布

## 6. 国内公安旅业系统作为核心领域

第二阶段不再把公安登记视为外部脚本，而是建立独立的 `Compliance/Police Registration` 领域服务。

### 6.1 领域对象

- `identity_sessions`：一次证件读取和核验会话
- `guest_identity_tokens`：短期身份引用，不保存模型可读原文
- `police_registrations`：登记业务记录
- `police_submission_attempts`：每次提交和查询尝试
- `police_receipts`：回执摘要、外部编号和校验信息
- `manual_compliance_tasks`：验证码、特殊证件、拒绝和补报任务
- `data_retention_policies`：门店/属地保存和删除策略
- `consent_or_notice_records`：需要留存的告知和授权记录

### 6.2 权威边界

| 事实 | 权威来源 |
| --- | --- |
| 证件原始字段 | 门店受控身份区和经批准的读卡系统 |
| 人证核验结果 | 合法核验设备或服务回执 |
| 公安登记是否受理/成功 | 属地旅业系统回执 |
| PMS 入住状态 | AI 原生 PMS 入住服务 |
| 门锁凭证是否生效 | 门锁控制器回执 |

PMS 可以记录公安状态，但不能自行声明公安登记成功。公安服务可以阻止无人入住继续，但不能直接修改账务或房态。

### 6.3 多属地适配

建立 `PoliceAdapter` 契约：

```text
capabilities()
validateGuestPayload()
submitRegistration()
querySubmission()
amendRegistration()
cancelOrCheckoutRegistration()
healthCheck()
```

每个适配器声明：支持的证件、字段、操作、网络要求、证书方式、是否需要人工、重试规则、回执格式和版本。门店在上线配置中绑定一个经过验收的适配器版本，禁止运行时由 AI 任意切换。

### 6.4 隐私和安全控制

- 身份数据默认在门店处理；确需跨区域传输时单独完成合法性、必要性和安全评估。
- 数据采集页面明确告知用途、处理方式、保存范围和联系渠道。
- 生物识别、证件照片等敏感个人信息使用更严格的权限和加密策略。
- AI、经营分析、客服知识库与身份原始数据物理或逻辑隔离。
- 禁止在日志、错误追踪、模型提示、截图和测试夹具中写入真实证件数据。
- 测试环境只使用公安许可的测试数据或完全虚构数据。
- 调阅身份原文需要专门权限、业务原因和二次审计。

### 6.5 公安流程门禁

正常入住要求以下事实全部成立：

1. 订单和入住资格有效。
2. 客人身份核验完成。
3. 所有需登记的住客已创建登记记录。
4. 公安系统返回可校验的成功状态。
5. 房间锁定有效。
6. PMS 入住确认成功。
7. 门锁凭证生成并验证成功。

任何状态为未知时，系统不得推断成功。只有属地允许且门店预案明确的特殊流程，才可以通过人工审批进入后续步骤。

## 7. AI 产品形态

### 7.1 客人 Agent

- 查询、报价、预订和入住说明
- 自助入住过程指导
- 设施、交通和本地信息
- 续住、延迟退房和投诉申请
- 多语言沟通

### 7.2 前台 Agent

- 订单检索、分房建议、换房和异常解释
- 身份与公安状态提示
- 账单解释、发票申请和人工接管
- 交接班摘要

### 7.3 房务 Agent

- 清扫和维修任务编排
- 根据到店时间与房态排序
- 延误、质量和重复故障识别

### 7.4 收益 Agent

- 读取库存、预订曲线、周边活动和竞品价格
- 给出价格建议和收入影响
- 经规则引擎限制后进入自动或人工发布

### 7.5 老板 Agent

- 经营日报、渠道净收入、人工成本和异常分析
- 支持自然语言追问并展示数据来源
- 不直接修改财务口径和历史账务

## 8. 服务架构

首期推荐模块化单体，避免过早拆分微服务。领域之间通过明确接口和事件通信，待多门店规模和团队边界稳定后再拆分。

建议模块：

- Tenant & Hotel
- Catalog & Rate
- Order
- Reservation
- Inventory & Room
- Guest & Identity
- Check-in & Stay
- Folio & Ledger
- Payment & Refund
- Housekeeping & Maintenance
- Channel
- Device
- Compliance / Police
- Workflow
- AI Orchestration
- Audit & Reporting

## 9. 单一事实来源

| 事实 | 自有权威模型 |
| --- | --- |
| 商业订单金额和状态 | `orders` / `order_items` |
| 住宿日期和预订状态 | `reservations` |
| 实体房间状态 | `rooms` / `room_status_logs` |
| 房间分配 | `room_assignments` |
| 实际入住 | `check_ins` / `stays` |
| 账务 | `folios` / `ledger_entries` |
| 支付与退款 | `payments` / `refunds` |
| 公安登记 | `police_registrations` / `police_receipts` |
| 外部命令 | `external_commands` |
| AI 与人工任务 | `workflow_runs` / `manual_tasks` |

禁止使用演示投影、缓存或 AI 记忆反向覆盖正式事实。

## 10. 迁移策略

### 第一步：影子副本

从现有 PMS 同步订单、预订和房态，自有系统只读并对账。

### 第二步：单模块接管

优先接管任务、房务、设备和 AI 工作流，原 PMS 继续负责账务和房态。

### 第三步：订单与房态接管

自有系统成为预订和房态权威，旧 PMS 接收投影或作为人工备用。

### 第四步：入住与账务接管

自有系统负责入住、账本、支付、退款和夜审。完成平行账期对账后关闭旧写入。

### 第五步：旧 PMS 退出

保留历史查询、数据导出和回滚窗口，逐门店停止旧 PMS。

每次切换都必须有明确的回退点、双写期限、差异报告和负责人。

## 11. 研发阶段与任务

### Phase 2A：正式领域模型

- 完成订单、预订、房间、分房、入住、账务、支付和退款模型。
- 清除演示表作为生产写入目标的路径。
- 完成版本并发、唯一占用、状态日志和正式审计。

出口标准：同一房间不能同时分配给两笔有效入住；订单金额、预订状态和房态各自只有一个权威来源。

### Phase 2B：核心运营闭环

- 创建预订、锁房、入住、消费、支付、退房、清扫和恢复可售。
- 建立夜审、交班、支付对账和异常账务人工流程。
- 公安、门锁、支付和发票继续使用第一阶段连接器。

出口标准：单店可在无旧 PMS 写入的情况下完成完整营业日并对账。

### Phase 2C：公安与无人入住生产化

- 将目标城市适配器接入正式 Compliance 服务。
- 支持居民身份证、境外人员和特殊证件的分流；具体自动化范围以属地允许为准。
- 完成断网、回执未知、补报、撤销、离店和人工接管。
- 完成门店级隐私策略、数据保留和安全审计。

出口标准：属地测试环境和样板店验收通过；任何登记未知均不会自动发卡。

### Phase 2D：AI 原生运营

- 上线客人、前台、房务、收益和老板 Agent。
- 建立 Agent 评测集、工具权限、模型降级和人工确认。
- 引入主动事件：到店异常、房务延误、库存风险和价格机会。

出口标准：Agent 在验证集和影子运行中达到目标准确率；高风险操作越权为 0。

### Phase 2E：多门店与商业化

- 集团组织、门店隔离、统一会员和集团报表。
- 门店模板、连接器市场、设备批量管理和远程运维。
- 支持按门店、房间数、任务量或 AI 使用量计费。

## 12. 关键非功能要求

### 可用性

- 云端不可用时，门店 Worker 保留必要的设备状态和待处理任务。
- 断网不等于自动放行；按门店应急预案决定是否转人工。
- 所有进行中流程在服务重启后可恢复。

### 性能

- 普通读查询目标 P95 小于 500ms，不含外部系统耗时。
- Agent 首次反馈目标小于 2 秒，长任务持续展示步骤状态。
- 外部系统调用采用独立超时和熔断，不占满核心服务线程。

### 安全

- 所有生产 API 强制门店作用域、服务身份和最小权限。
- 高风险操作要求二次确认或双人审批。
- 密钥进入专用密钥管理，不出现在代码、数据库普通字段和日志中。
- 管理后台会话、设备证书和服务账号分别管理。

### 可观测性

- 统一 `trace_id` 关联 AI、业务、连接器、设备和公安回执。
- 指标覆盖订单差异、库存冲突、登记失败、设备离线、支付未知和人工接管时长。
- 告警不得包含完整身份证、手机号、证件照片或支付凭据。

## 13. 测试体系

- 领域状态机测试
- 金额和账务不变量测试
- 并发锁房和分房测试
- 幂等重放测试
- 连接器契约测试
- 公安、支付、门锁故障注入
- 服务重启和工作流恢复测试
- 门店断网、断电和备用设备演练
- Agent 工具选择和越权测试
- 敏感信息泄漏扫描
- 双系统迁移差异和账务对账测试

## 14. 验收指标

- 房间双重占用为 0。
- 账务流水不平和无法追溯的金额变更为 0。
- 公安、支付、PMS 或门锁状态未知被当作成功的次数为 0。
- AI 直接访问证件原文或生产数据库的次数为 0。
- 工作流、外部命令和人工任务均可通过统一链路追踪。
- 真实门店完成一个完整平行账期，订单、房态、支付和公安状态差异全部可解释。
- 旧 PMS 切换前完成回退演练和数据导出验证。

## 15. 团队与治理

建议建立产品、酒店运营、核心领域、连接器设备、AI、测试、安全合规七个责任域。公安和身份能力必须指定单独负责人；任何新城市上线需要重新完成属地调研、字段映射、接口验收、隐私评审和应急演练，不能沿用其他城市的验收结论。

重大设计决策通过 ADR 记录，至少覆盖：数据权威归属、账务模型、公安接入方式、身份数据存储位置、门店断网策略、旧 PMS 切换和高风险 AI 权限。

## 16. 立项出口

第二阶段进入生产建设前必须满足：第一阶段样板店已稳定运行；目标门店提供完整业务流程和对账样本；属地公安接入方式已经确认；PMS 迁移范围和回退策略已经签字；账务和支付模型通过专项评审；有明确的远程值守和现场应急机制。
