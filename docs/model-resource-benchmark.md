# Hotel Agent OS 模型资源与压测量化方案

## 1. 文档目的

本文用于量化 Hotel Agent OS 完成一次完整自助入住时的：

- 大模型输入、输出及累计 Token 使用量；
- 语音识别、RAG、工具调用、数据库和语音合成延迟；
- RTX 3090 单卡及双卡环境中的显存、吞吐与并发能力；
- 不同 Qwen 模型在问答、RAG 和工具调用方面的适用范围；
- 正式压测方法、样本数量和验收标准。

> 当前数字为工程预算值，不是现有演示站点的实测结果。现有演示站点尚未接入真实大模型，因此当前大模型 Token 消耗为 0。接入模型服务后，应由压测程序填写“实测结果”。

## 2. 测试前提

首轮测试采用以下条件：

- 一次完整入住包含约 12 次大模型调用；
- 每次请求都携带完整历史，不裁剪、不摘要；
- 允许开启前缀缓存，但不能删除模型可见的历史内容；
- RAG 每次返回 3～5 个相关片段；
- 订单、房态、支付、身份和登记数据通过确定性工具查询，不使用向量相似度代替业务主键；
- 所有测试均使用假订单、假身份 Token 和公安浏览器隔离模拟环境；
- RTX 3090 24GB 作为单卡基线，并补充双 RTX 3090 和 48GB 显卡参考；
- 对话模型采用 4 位量化版本进行单卡测试。

## 3. 完整业务链路

```text
客人语音
  ↓
VAD 判断说话开始与结束
  ↓
FunASR 流式语音识别
  ↓
Qwen 对话与工具选择
  ├── WeMM-Embedding + 向量数据库：酒店知识检索
  ├── 订单数据库 / PMS：精确业务数据
  ├── 身份核验服务：返回脱敏结果
  ├── 公安浏览器 Worker：隔离模拟或授权环境
  └── 人工工单：异常接管
  ↓
Qwen 根据工具回执组织回答
  ↓
CosyVoice 或其他 TTS 流式语音合成
  ↓
终端音箱播放
```

WeMM-Embedding 只负责检索，不负责回答或语音输出。自然语言回答由 Qwen 生成，声音由 TTS 模型生成。

## 4. 一次完整入住的 Token 预算

按 12 次模型调用、完整历史重复发送计算：

| 数据来源 | 累计输入 Token 预算 |
| --- | ---: |
| 系统规则与安全约束 | 约 42,000 |
| 工具接口定义 | 约 30,000 |
| 客人与 AI 的历史对话 | 约 25,000～40,000 |
| 数据库、PMS 等工具回执 | 约 20,000～35,000 |
| RAG 检索片段 | 约 20,000～40,000 |
| **累计输入总量** | **约 137,000～187,000** |
| **累计输出总量** | **约 1,500～3,000** |

最后一轮请求的单次上下文预计为 20,000～30,000 Token。累计输入量高于最后一轮上下文，是因为每轮都会再次处理之前的历史。

### 4.1 建议记录字段

每次模型请求至少记录：

```json
{
  "model": "Qwen3.5-27B-Q4",
  "case_id": "DEMO_CASE_ID",
  "turn": 6,
  "prompt_tokens": 12480,
  "completion_tokens": 156,
  "cached_prompt_tokens": 10320,
  "rag_tokens": 1280,
  "tool_schema_tokens": 2500,
  "time_to_first_token_ms": 1850,
  "generation_tokens_per_second": 27.4,
  "time_to_first_audio_ms": 2640,
  "gpu_memory_peak_mb": 22480,
  "tool_name": "pms_hold_room",
  "tool_success": true
}
```

不得在压测日志中记录真实姓名、完整手机号、身份证号码、证件照片、支付凭据或有效公安登记字段。

## 5. 不控制上下文时的速度预算

### 5.1 不开启前缀缓存

- 前几轮开始回答：约 1.5～3 秒；
- 中间轮次开始回答：约 3～8 秒；
- 后期长上下文开始回答：约 8～20 秒；
- 一次入住的大模型累计计算时间：约 3～6 分钟。

### 5.2 开启前缀缓存

前缀缓存不删除上下文，只复用未变化的历史计算结果：

- 普通问答开始回答：约 1.5～3 秒；
- 后期长对话开始回答：约 2～5 秒；
- 一次入住的大模型累计计算时间：约 30～90 秒；
- 加上客人说话和外部工具，一次完整办理预计约 2.5～5 分钟。

因此，首期可以不裁剪上下文，但生产测试必须开启并统计前缀缓存命中率。

## 6. 各环节延迟预算

| 环节 | 单次预算 |
| --- | ---: |
| VAD 判断客人说完 | 300～600 ms |
| FunASR 流式语音识别收尾 | 200～800 ms |
| RAG 向量检索 | 20～200 ms |
| 本地数据库查询 | 10～100 ms |
| Qwen 首 Token | 500～5,000 ms，取决于模型、上下文和并发 |
| TTS 首段声音 | 150～600 ms |
| PMS 请求 | 100～3,000 ms，取决于第三方系统 |
| 公安浏览器任务 | 5～20 秒或更长，取决于页面和网络 |

公安浏览器或 PMS 执行期间，AI 应先播放等待反馈，不应让客人面对无响应页面。

## 7. RTX 3090 模型资源预算

以下为 4 位量化、20K～30K 上下文的工程估算：

| 模型 | 显存峰值预算 | 生成速度预算 | 建议单卡并发 | 适用范围 |
| --- | ---: | ---: | ---: | --- |
| Qwen3.5-9B | 8～12GB | 40～80 Token/s | 4～8 路 | 速度基线、标准问答和固定流程 |
| Qwen3.5-27B | 20～24GB | 18～35 Token/s | 1～2 路 | 主要生产候选，复杂问答和工具编排 |
| Qwen3.5-35B-A3B | 21～24GB | 30～60 Token/s | 1～3 路 | MoE 对照，需重点测试长上下文 OOM |
| 双 RTX 3090 运行 27B | 总占用约 30～40GB | 25～50 Token/s | 4～8 路 | 多终端中央推理服务 |
| 48GB 显卡运行 27B | 25～35GB | 25～50 Token/s | 4～8 路 | 稳定生产候选 |

### 7.1 单张 RTX 3090 的显存分配

```text
Qwen3.5-27B 四位量化权重及运行开销：约 16～19GB
20K～30K 上下文、KV Cache 和框架开销：约 3～5GB
总计：约 20～24GB
```

一张 3090 不适合同时常驻 Qwen3.5-27B、WeMM-Embedding-4B 和大型 TTS。建议：

```text
RTX 3090：Qwen3.5-27B
CPU：FunASR、VAD、业务接口
CPU 或按需 GPU：WeMM-Embedding-2B
云端或第二张显卡：TTS
系统内存：至少 64GB
```

## 8. RAG 数据规模预算

WeMM-Embedding 支持 2B、4B 和 9B 模型，并支持不同向量维度。酒店首期建议采用 WeMM-Embedding-2B 和 512 或 1024 维向量。

| 知识片段数量 | 向量与索引占用预算 | 典型用途 |
| --- | ---: | --- |
| 5,000 | 10～100MB | 单店政策、房型、服务和设备资料 |
| 20,000 | 50～250MB | 多店资料及维修手册 |
| 50,000 | 100～500MB | 酒店集团知识库 |
| 100,000 | 200MB～1GB | 大型多模态知识库 |

订单状态、房态、身份证、支付、价格和房卡状态不得写入通用 RAG 并依赖相似度查询，必须通过数据库或正式业务接口精确读取。

## 9. 完整入住压测场景

每次完整入住包含：

1. 欢迎与能力说明；
2. 早餐、停车或退房政策问答；
3. RAG 检索酒店资料；
4. 手机号后四位输入与复述确认；
5. 订单数据库查询；
6. 订单脱敏信息确认；
7. 身份证放置与核验；
8. 房态查询；
9. 锁房；
10. 押金和房型问答；
11. 公安浏览器登记模拟；
12. 登记回执读取；
13. 发卡机自动写卡、回读校验与吐卡；
14. 传感器确认身份证和房卡均已取走；
15. Wi-Fi、早餐位置等入住后问答。

异常用例包括：

- 手机号后四位命中多笔订单；
- 已入住订单重复办理；
- 已取消订单；
- 无线上订单转现场办理；
- 身份证遗留、重复读取或信息不符；
- 发卡机缺卡、卡槽堵塞、写卡失败、回读不一致或取卡超时；
- 房态冲突；
- PMS 超时；
- 公安页面验证码、证书错误或维护；
- 模型输出非法工具参数；
- 重复工具调用；
- GPU 显存不足或模型队列超时。

## 10. 压测数量

每个模型执行：

- 5 次预热；
- 并发 1、2、4、8 路；
- 每种并发执行 30 次完整入住；
- 每个模型共 120 次完整入住；
- 按每次 12 次模型调用计算，每个模型约 1,440 次请求；
- 三个模型共 360 次入住、约 4,320 次模型调用；
- 额外执行 2 小时、4 路并发持续稳定性测试；
- RAG 分别使用 5,000、50,000、100,000 个知识片段测试。

## 11. 必须输出的统计结果

报告至少包含：

- P50、P95、P99 首 Token 延迟；
- P50、P95、P99 首段语音延迟；
- 平均及最低生成 Token/s；
- 单次和累计输入、输出、缓存 Token；
- RAG 检索耗时和召回准确率；
- 工具选择正确率、参数正确率和执行成功率；
- GPU 利用率、显存峰值、温度和功耗；
- CPU、系统内存和磁盘占用；
- 排队时间、超时率、OOM 次数和请求失败率；
- 重复锁房、重复登记和非法状态跳转次数。

## 12. 验收标准

| 指标 | 合格标准 |
| --- | ---: |
| 单路首段语音 P95 | 小于 3 秒 |
| 两路并发首段语音 P95 | 小于 5 秒 |
| 四路并发首段语音 P95 | 小于 8 秒 |
| RAG 查询 P95 | 小于 300 ms |
| 普通数据库查询 P95 | 小于 200 ms |
| 工具选择正确率 | 不低于 99% |
| 关键状态跳转正确率 | 100% |
| 重复锁房、重复登记 | 0 次 |
| 非法越权工具调用 | 0 次 |
| OOM | 0 次 |
| 压力过高时的行为 | 允许排队，不允许错误放行 |

## 13. 初步结论

- 单张 RTX 3090 运行 Qwen3.5-27B 四位量化版，适合 1～2 台终端同时办理；
- 4 台以上终端建议使用双 RTX 3090、48GB 显卡或中央推理集群；
- Qwen3.5-9B 更快、并发更高，但必须重点验证复杂问答和连续工具调用；
- Qwen3.5-35B-A3B 可能提供更高吞吐，但单张 3090 的长上下文显存空间较紧；
- 不裁剪上下文可以作为首轮测试条件，但必须开启前缀缓存并记录缓存命中率；
- RAG 不是主要性能瓶颈，27B 对话模型的上下文预填充、KV Cache 和并发排队才是主要压力；
- 生产结论必须以相同硬件、量化格式、推理框架和真实完整入住脚本的实测数据为准。
