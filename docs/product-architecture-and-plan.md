# Hotel Agent OS 产品架构与实施计划（敲定稿）

编制日期：2026-09-20
本文把「两个入口、一个酒店大脑」的产品设计与当前代码现状合并，作为后续开发的唯一对齐基准。

## 1. 产品形态

**两个入口，一个大脑。**

- 入口 A · 身份证：办理入住——核实身份 → 查询预订 → 确认入住资格 → 分房 → 制卡 → 完成入住。
- 入口 B · 房卡：办理退房/换房——识别房卡对应的有效入住记录，退房或换房。
- 一个大脑：AI 对话层 + 上下文编排器 + 三层记忆（Session / Stay / Member）。
- 统一业务系统：身份验证、预订、订单、支付、分房、房卡管理，落同一套正式数据库。

入口分开让客人操作简单；后台只有一套订单、一套预订、一套房态，不会长出两套事实。

## 2. 三条不可动摇的原则

1. **事实不可变，状态可推导。** 事实有唯一权威表；状态由权威表推导，不留第二份真相。
2. **识别是线索，不是授权。** 身份证/房卡被识别，只代表拿到了查找业务记录的线索；完成必要核验前不得展示私人资料。
3. **清除的是终端痕迹，不是业务数据。** 公共终端的会话痕迹要彻底清；客人的正式业务数据与管理审计不在清除范围，个人信息删除走独立合规流程。

## 3. 目标架构

```text
客人 / 自助终端
   │
   ▼
AI 对话层
   │
   ▼
AI 上下文编排器
   │
   ├─ Session Memory（本次会话）
   ├─ Stay Memory（本次住宿）
   └─ Member Memory（会员，绑定手机号哈希后解锁）
   │
   ▼
受控业务工具（AI 不直写库）
   │
   ├─ 预订服务
   ├─ 分房服务
   └─ 酒店服务
   │
   ▼
正式业务数据库
```

编排的是上下文，不是权限；会员不会因为“是老客”获得更宽的写权限。

## 4. 数据分类（唯一口径）

| 类别 | 内容 | 载体 | 生命周期 |
| --- | --- | --- | --- |
| 正式业务数据 | 订单、预订、房态、入住、账务 | `orders`/`reservations`/`rooms`/`stays`/`folios`/`ledger_entries` | 按业务与审计要求保留 |
| 会员长期记忆 | 经确认的偏好 | 待建 `guests`/`member_memory`/`consent_records` | 会员存续期内，可撤回 |
| 会话临时数据 | 对话、临时身份结果、未确认需求 | 会话层 + 脱敏 `ai_*` | 会话结束后失效 |

前台不直连数据库，只走受控 API；浏览器 `localStorage` 不保存身份证号、手机号、房号、会员档案或订单详情。

## 5. 会话隔离（四道保护）

1. **独立 Session**：每位客人一个随机会话 ID，服务端把会话绑定到终端、已验证身份与权限范围。
2. **上下文按 Session 构建**：AI 只使用当前会话允许访问的数据，不把整台自助机的历史聊天当连续对话。
3. **后台强制权限**：查询订单、会员偏好、入住资料时按当前有效会话核验范围，前端误传他人 ID 也拿不到数据。
4. **结束彻底失效**：结束后服务端立即拒绝旧会话的新操作；前台清空状态、停止语音流、取消异步任务；旧请求的迟到结果必须因会话代次不匹配而丢弃。

终端状态机：等待客人 → 正在办理 → 超时提醒 → 会话结束。倒计时不中断真实支付或制卡；这类操作由后台继续确认并进入可恢复状态。

## 7. 分阶段落地

| 阶段 | 目标 | 交付 |
| --- | --- | --- |
| P0（已基本完成） | 事实收口 | `orders` SSOT、并发幂等、离店账务、AI 决策链、缺陷治理 |
| P1 · 会话隔离 | 两个入口的公共终端安全 | 服务端会话凭据+绑定、服务端组装上下文、退房/账务按会话收口、超时状态机 |
| P2 · 分房与房卡 | 入口 B 可落地 | `room_assignments`、`key_credentials`、锁定期与释放、插卡识别 |

| P4 · 多步与知识 | Agent 化 | B2 多步编排、B3 知识与记忆、B4 主动性 |

## 8. 验收标准

- P1：A 的订单/账单不会被 B 拿到；旧会话迟到响应被丢弃；退房查询只能命中当前会话授权范围。
- P2：并发抢同一房间只成功一次；锁房超时自动释放；旧房卡权限在换房/退房完成后被撤销。
- P3：未成会员只存当次住宿所需脱敏事实；成为会员后才按手机号哈希归并长期记忆；同意可撤回。
- P4：复合诉求可线性拆解完成，断网可恢复；政策问答来自知识库；主动事件可度量、可关闭。

## 11. 会话隔离的具体做法

分两层，不要混：

- **终端会话 session**：代表「这一个人在机器前这一次办理」。由服务端创建，绑定终端、租户/酒店、创建时间、状态、身份核验等级、当前案件/订单。
- **对话 conversation**：代表「同一段对话线程」。一个 session 内可有多轮对话，换一段对话不等于换一个人。

机制：

1. **服务端发凭据**：客人开始时服务端生成 `session_id` 与一次性令牌；前端只持有令牌，所有请求带令牌。服务端从令牌反查 session，**不信任前端传的 session_id、订单号、案件号**。
2. **身份等级随会话升级**：`unverified → card_read → identity_verified`。查询私人资料的接口要求等级达标；读卡只是线索，等级不够不返回任何客人数据。
3. **上下文服务端组装**：前端只发「这一句话」，历史、案件、订单、住宿由服务端按 session 取；不再接受前端整段 messages。
4. **收口所有按人查询**：订单、账单、入住、会员记忆一律 `WHERE session 授权范围`；退房/账务查询必须补上会话过滤。
5. **结束即失效**：会话置 `ended/revoked`，后续请求直接拒绝；前端清屏、停麦、取消异步任务；响应带会话代次，代次不符的一律丢弃（前端已实现，服务端要补）。
6. **超时分两级**：普通问答短空闲 → 提醒 → 自动结束；支付/制卡等不可中断状态标记为「后台继续确认」，倒计时不打断，结果进入可恢复状态。

## 12. 会员信息收集的具体做法

原则：**入住不要求办会员；会员记忆必须「自愿 + 明确同意 + 可撤回」。**

收什么：

| 字段 | 处理方式 |
| --- | --- |
| 手机号 | 只作绑定键：存 `phone_hash` + 后四位；明文不落库，不写日志 |
| 姓名 | 脱敏存储 |
| 同意记录 | 谁、何时、同意哪一版政策、用途、撤回状态（必须落库） |
| 身份证影像 / 支付凭证 | **不收集、不存储** |

什么时候收：

1. 入住/退房流程走完或进行中，主动询问是否办理会员，**拒绝不影响任何业务**。
2. 同意后写 `consent_records`，并把本次住宿与该会员身份用 `phone_hash` 关联。
3. **会话中不写会员记忆**；离店后由系统提炼「可复用偏好」（如高层、安静、不要靠电梯），带来源与置信度写入会员记忆。
4. 客人可查看、修改、删除自己的记忆；撤回同意后停止使用并可删除。
5. 未成会员：只保留当次住宿所需的脱敏事实，会话结束即失效，**不做跨会话画像**。

下次识别：客人再次到店并完成手机号验证（或读卡 + 手机号确认）后，才按 `phone_hash` 解锁该会员记忆。

待建表：`guests`（档案，主键 phone_hash）、`member_memory`（结构化偏好 + 来源 + 置信度）、`consent_records`（同意与撤回）。
