# 门店知识库（RAG 的第一版）

## 1. 为什么要有它

在它之前，"门店政策"是**写死在代码里的四句话**：

- `lib/tools.ts` 只能识别四个话题（`breakfast | parking | payment | checkout`）；
- 答案硬编码在**两个地方**（`app/page.tsx`、`app/api/demo/[action]/route.ts`），改一次政策要改两处代码；
- 代码注释里早就写着"正式接入后，这里会读取当前酒店的知识库配置"——这个承诺现在兑现了。

- **向量检索**：`vectorize` 槽位在 wrangler 配置里是空的；等**语料**和**评测集**都到位再上，混合检索是第二步不是第一步。现在上向量只会让「为什么答错了」更难查。
- **语料来源**：门店政策文档还没人写——这是当前真正的瓶颈。后台已经能录了，但录什么还得人来写（建议先用 ima 之类的知识工作台把政策、FAQ、SOP 整理出来，再按「一行一条」录进去）。
- **评测集扩容**：现在是 38 条（含 11 条硬负例）。客人真实问法进来之后要继续往里加；边界用例（同域但语料未覆盖）目前只统计不判失败，等语料长起来再逐步收严。
- **停用字表还会长**：停用字是「虚词名单」，每加一个字都可能误伤内容词（「地」就是例子）。评测集是唯一能挡住这类回归的东西，所以它必须在 CI 里。

**现状：`hotel.policy_answer` 不再返回写死的字符串，而是返回「命中了哪份文档哪一版」，命中不到就转人工。**

## 2. 数据模型（三张表 + 一张 FTS）

| 表 | 作用 |
| :--- | :--- |
| `knowledge_documents` | 文档：标题、来源（`policy`/`faq`/`sop`/`ticket`）、权威度（`authoritative`/`reference`/`hint`）、可见范围（`guest`/`staff`）、版本、生效期、状态 |
| `knowledge_chunks` | 切片：正文、关键词、以及**写入时切好的二元词**（`bigrams`） |
| `knowledge_chunks_fts` | FTS5 虚表：对 `bigrams` 建索引 |

迁移：`drizzle/0019_knowledge_base.sql`（同时预置了门店政策 v1：早餐、停车、支付与押金、退房，外加一篇**员工可见**的延迟退房加收标准，用来验证权限隔离）。

## 3. 中文检索：为什么要自己切二元词

D1 的 SQLite 支持 FTS5，但两个分词器都不好用：

- **默认 `unicode61`**：会把一整串中文当成**一个**词，"早餐几点开始"匹配不到"早餐时间"；
- **`trigram`**：实测能匹配 3 字以上（`早餐时` 命中），但**中文两字查询（"早餐""停车""押金"）完全命中不了**——而两字恰恰是最常见的问法。

所以切片时就把正文切成**二元词**（"早餐时间是…" → `早餐 餐时 时间 间是 …`），关键词也一起切进去，检索时把查询同样切成二元词去匹配。实测四种两字查询全部命中。

## 4. 检索规则（比选型更重要的部分）

1. **权限过滤是 WHERE 的第一条件**：客人只能命中 `visibility = 'guest'`，员工可命中 `guest + staff`；不是先检索再筛。
2. **只取此刻生效的**：`status = 'active'` 且 `effective_from <= now`、`effective_to` 为空或未过期。
3. **改版先清后写**：`replaceKnowledgeChunksWith` 先删旧切片与索引行，再写新的，避免半新半旧。
4. **覆盖率阈值**：命中需要覆盖查询里足够多的字（去停用词后的单字覆盖，阈值 `0.34`），低于阈值**宁可说不知道**。
   - 覆盖率用的是**单字**而不是二元词：二元词适合建索引，不适合算覆盖率——"早餐几点"的二元词只有 1/3 落在文档里，会把一次正确命中的考成"查不到"（这是测试当初抓出来的真缺陷）。
5. **命中不到就转人工**：`needs_handoff = true`，话术是"这个我暂时没有可靠依据（门店知识库里没查到），已记录并转前台确认"。**绝不让模型自己编一条政策。**
6. **停用字只收虚词**：覆盖率与字对都会先剔除疑问词/虚词，但**只剔虚词**。「地」曾经因为「地点」被收进停用字，代价是把「地库」这个字对一起拆掉——客人问「地库怎么走」时命中不到停车政策（评测集逮到的真缺陷），修法是把「地」移出停用字集合。
7. **命中不到再由兜底决定**：答案取「第一条够格的命中」而不是「第一条」——排序里可能有一条只是沾边的切片排在最前，把它当成唯一判断依据，就会把一次答得出来的问题判成转人工。
8. **每条回答带出处**：`citations` 含文档标题、版本、生效期，终端会把"依据：早餐时间与服务 v1"一起显示。

## 5. 接在哪里

| 入口 | 行为 |
| :--- | :--- |
| `POST /api/demo/knowledge-search` | 新动作：`{ query }` 或 `{ topic }` → 答案 + 出处 + 是否转人工 |
| `app/api/demo/[action]/route.ts` 的 `interpret` | 政策意图（`action = "rag_answer"`）改为查知识库，答案与出处由服务端给 |
| `lib/tools.ts` | 新增工具 `hotel.knowledge_search { query }`；`hotel.policy_answer` 保留四个老话题，并额外带上原始问句 |
| 兜底路由 | **任何像"提问"的话**（含 吗/怎么/多少/几点/有没有…）都先交给知识库，由它决定答不打得出来——而不是让关键词表决定"哪些问题我们才认" |
| 管理后台 | **政策知识库面板**：列表 / 编辑 / 停用 / 重新生效 / 试问，全部走 `admin.*` 工具，不需要写 SQL |
| 前端 | 不再自己拼政策话术，直接展示服务端答案与出处；失败时也不编，保持转人工话术 |

审计：每次查询写一条 `KNOWLEDGE_ANSWERED`，命中记「命中了哪几篇 v几」，未命中记「未命中」，便于事后统计**语料缺口**（哪些问题客人真的在问、而知识库里没有）。

## 6. 店长怎么改政策（后台录入面）

在这之前，改一条政策要写 SQL；现在店长在后台自己维护，但**能改答案的动作照样要过一次人工确认**。

| 工具 | 作用 | 权限 |
| :--- | :--- | :--- |
| `admin.list_knowledge_documents` | 列出这家店的全部文档：状态、可见范围、版本、切片数、生效期 | `admin:manage_knowledge` |
| `admin.get_knowledge_document` | 读一篇文档的正文（切片） | `admin:manage_knowledge` |
| `admin.preview_knowledge_answer` | **试问**：客人这么问，系统会答什么、命中哪一篇、覆盖率多少 | `admin:manage_knowledge` |
| `admin.prepare_knowledge_document` | 新建/改版：正文 + 「其他说法」（关键词，进索引）+ 可见范围，先生成确认单 | `admin:manage_knowledge` |
| `admin.prepare_knowledge_status` | 停用 / 草稿 / 重新生效：同样先生成确认单 | `admin:manage_knowledge` |

几条设计取舍：

1. **一行就是一条切片**。后台输入框里的一行 = 客人可能被答到的一句话；切片入库时现切二元词，和迁移预置语料走同一条 `replaceKnowledgeChunksWith`。
2. **改版自动升版本**。店长不用记版本号；改完是 v2、v3，出处里跟着显示。旧切片整篇替换，不留半新半旧。
3. **停用不删切片**。停用只是让它检索不到（客人问不到 → 转人工），内容留着，停错了可以「恢复生效」。
4. **可见范围是可赔钱的那条线**。选「客人可见」= 这条会作为终端上的答案与出处出现；涉及加收、赔付、内部底价的内容应当选「仅员工可见」（员工文档客人身份永远检索不到）。
5. **试问走终端同一条检索路径**（同一个 `answerKnowledgeQuestionWith`），所以店长看到的就是客人会看到的。写完先试问，是这套东西能不能自证的唯一办法。
6. **权限**：`admin:manage_knowledge` 只给 owner 与 manager；前台、客房拿不到（他们可以问客人问题，但不能改客人拿到的答案）。未登录一律 401。
7. **审计**：每次准备与执行都写 `ADMIN_KNOWLEDGE_DOCUMENT_PREPARED/SAVED`、`ADMIN_KNOWLEDGE_STATUS_PREPARED/CHANGED`，记下谁、什么时候、改了哪份文档的哪一版。
8. **「其他说法」不是可选装饰**。检索按字匹配，正文写「地下一层」而客人问「车库」，字对碰不上就答不出来。所以表单里单独有「客人可能用到的其他说法」一栏（空格分隔），它和正文一样进索引、一样进覆盖率。这一栏不是我们发明的：迁移里预置的语料本来就有 `keywords`（车位/停车费/停车/车库），后台编辑时必须能把它读回来再写回去 —— 否则店长改一次正文，就把原有的召回悄悄改坏了（这条也是测试逮出来的）。

**改语料不能只改迁移文件。** 迁移里的语料是 `INSERT OR IGNORE`，已经迁移过的库不会被更新 —— 我们把预置停车政策从「地下一层」改成「地库（地下一层）」时，评测（读迁移文件）已经是 26/26，而演示库（读自己的表）还是旧正文，客人问「地库怎么走」照样转人工。**线上那份在表里，表才是真相**：改预置语料要么写一条新的迁移去 `UPDATE`，要么在后台按「改版」走一次（我们这次就是把「停车服务」改成 v2，顺带把「地库」同步进演示库）。

## 7. 验收

- `scripts/test-knowledge-d1.mjs`（**27 项，真实 D1**）：中文两字查询命中、关键词召回、出处完整、客人看不到员工文档、未生效/已过期/已归档不命中、改版后只命中新版本且索引无残留、命中不到转人工、检索只读、参数校验。
- `scripts/test-knowledge-admin-d1.mjs`（**55 项，真实 D1**）：列表/详情、16 类坏输入全部被拒、生效日归一（失效日按当天最后一毫秒，写「生效至 9-30」就管满 9-30）、新建即可检索、改版自动升版本且旧正文从切片与 FTS 里一起消失、停用后客人问不到但切片还在、恢复后又能查到、跨门店隔离、改不存在的文档被拒（不会悄悄新建）、**关键词召回**（正文里没有的说法只靠关键词命中；同一段正文不给关键词就答不出来，用来证明上一条不是碰巧）、关键词整篇替换而非累加。
- `scripts/test-knowledge-eval-d1.mjs`（**召回评测，进 CI**）：`fixtures/knowledge-eval.jsonl` **38 条**（26 正例 / 11 硬负例 / 1 边界），语料直接取迁移 0019（评测跑的就是上线的那份）。底线是正例命中率 ≥ 90% 且**硬负例一条都不许答**；**当前 26/26 = 100% · 命中错文档 0 · 硬负例误答 0**。
- `scripts/acceptance-knowledge-admin.mjs`（**真机 HTTP，27 项**）：店长登录 → 录入 → 确认前客人查不到 → 确认后客人拿到新答案与出处 → 改版 v+1 → 试问 → 停用后转人工 → 前台/客房被 403 → 未登录 401 → 审计留痕。这条验收可重复跑（跑完 doc 处于停用态），并额外压「只写在关键词里的问法也能答」。

- 真机验证（2026-09-20，把演示库里的「停车服务」按后台改版到 **v2** 之后）：客人问 `地库怎么走` / `车库在哪里` / `停车费多少钱` / `有停车位吗` 全部命中「停车服务 v2」并带出处；改版前同一个问题（`地库怎么走`）是转人工的 —— 这就是「表里那份才是真相」的现场证据。
- 真机验证（2026-09-20，演示库打上 0019 后）：`早餐 / 停车 / 押金 / 几点退房` 全部命中并带出处；`早上几点可以吃早饭`、「地库怎么走」命中对应政策；`能开发票吗`、`你们有游泳池吗`、`有洗衣服务吗` **正确转人工**（语料里没有，不编）；客人问「延迟退房加收多少钱」只命中客人可见的退房政策，**没有泄露内部加收标准**。

## 8. RAG 与个人用户：一套管线，三条知识带

门店知识库只回答了「店里的政策是什么」。一旦要「认识这位客人」，就必须把**共享知识**和**个人知识**分开看 —— 但检索规则是同一套。

| 知识带 | 存在哪 | 只服务谁 | 命中不到时 |
| :--- | :--- | :--- | :--- |
| 门店知识带（共享） | `knowledge_documents` / `knowledge_chunks` | 全店，所有人问到的答案必须一致 | 转人工，绝不编一条政策 |
| 个人知识带（私有，会员） | 计划中的 `guest_memory` 等（**还没有表**） | 只有本人 | 当不知道，不拿猜的偏好去服务 |
| 会话临时带（用完即弃） | 当次会话上下文（不落库） | 这一次办理 | 不补，缺什么问什么 |

三条带共用同一套规则（也是这套 RAG 的四条硬规则）：**权限过滤在检索之前、只取此刻生效的版本、每条命中都要说得出出处、命中不到就不编**。所以它不是三套系统，是一套管线换了取值范围。

区别在「答什么」：门店带答「**政策是什么**」，可以原样念给客人；个人带答「**这位客人该怎么办**」，它只拼进上下文，不当政策引用。两者混用的典型事故是「把偏好当政策」（客人说「我上次就是 13:00 退的」变成「好的，13:00」）或「把政策当私人承诺」。

冲突的判定顺序是固定的：**政策 > 房态与库存 > 偏好**。政策是硬约束、房态是事实、偏好只是措辞与选项 —— **个人带只影响「怎么服务」，永远不影响「收多少钱」**；金额只能来自政策与订单。

个人带的写入与遗忘：会话里只**抽事实**（不下结论）→ 会员**确认**（绑定手机号 + 记忆同意记录）→ 落库时带**来源、时间、到期、协议版本**；客人说「别记了」即停用/删除并写审计，而账本与入住记录一行不动（事实不会因为被要求忘记就消失）。门店带靠 38 条评测集守召回；个人带**不拿评测集优化** —— 优化个人记忆就是在优化对某个人的画像。

现状（别把设计当实现）：门店带已有表、检索、评测、后台录入界面；**个人带还没有表**，只有会员门槛与会话隔离的设计。这段内容已同步进演示稿（P23–P25）。
