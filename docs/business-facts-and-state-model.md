# 业务事实与状态流转规范

版本：v0.1（草案）　编制日期：2026-09-19
定位：本文是《产品战略 V2》的配套规范，用于在写代码前固定「事实如何成立、状态如何推导、责任由谁承担」。所有条款需与验收用例双向绑定。

---

## 0. 为什么先写这份规范

`orders` 替代 `demo_orders` 只是把**一张表**收口了。如果不先固定事实定义，接下来会在入住、房态、房卡、财务之间重新长出多套互相矛盾的记录——只是矛盾的位置从「订单」搬到了「退房和退款」。

本规范的验收方式很简单：**每一条条款都要有一个跑在真实 D1 上的用例**。没有用例的条款视为未生效。

---

## 1. 三条基本原则

### 1.1 事实不可变，状态可推导

- **事实（Fact）**：一次不可变、带时间戳的写入。例如「2026-09-19T10:03Z 客人 X 在订单 O 上完成入住」。事实一旦成立，永不修改，只能追加反向事实。
- **状态（State）**：由事实推导出来的当前视图。例如「订单 O 当前状态＝在住」。

**为什么重要**：如果直接改状态，就没有办法回答「为什么它变成了这个状态」。而推导可以随时重算。当前 `order_status` 是直接改的，应逐步过渡为「写事实 + 推导状态」。

### 1.2 凭证不等于权限

房卡能开门，不代表它有权退房、退款或换房。凭证只用于**识别是谁**，权限由**经过验证的业务记录**决定。

推论：不能靠「有没有插入这张卡」判断客人是否离开，也不能靠「卡还在客人手里」判断客人是否在住。

### 1.3 一次操作只成功一次

重复插卡、重复点击、重复回调、网络重试，都不得产生重复副作用。每个有副作用的操作必须有幂等键，幂等键的生成规则属于接口契约的一部分。

## 2. 事实清单

每条事实都必须明确：判据、权威表、生效时点、幂等键、责任系统。

| 编号 | 事实 | 判据 | 权威载体 | 生效时点 | 幂等键 |
| --- | --- | --- | --- | --- | --- |
| F1 | 订单成立 | 收款成功且订单写入 | `orders` | `orders.created_at` | `(hotel_id, idempotency_key)` |
| F2 | 收款成功 | 支付渠道返回可核实成功 | `payments` | 渠道确认时间 | `(hotel_id, channel_txn_id)` |
| F3 | 预订确认 | 预订写入且未被取消 | `reservations` | `reservations.updated_at` | `(hotel_id, reservation_no)` |
| F4 | 房间分配 | 分配记录写入 | `room_assignments` | 分配时间 | `(hotel_id, stay_id, room_id)` |
| F5 | 入住成功 | 身份核验通过且房间已分配 | `check_ins` / `stays` | 核验通过时间 | `(hotel_id, stay_id)` |
| F6 | 换房完成 | 新房分配写入且旧房权限撤销 | `room_assignments` + `key_credentials` | 旧房权限撤销时间 | `(hotel_id, change_request_id)` |
| F7 | 住宿结束 | 退房操作成立（**与退款无关**） | `stays` | 退房确认时间 | `(hotel_id, stay_id)` |
| F8 | 结算单生成 | 结算规则执行完成并留痕 | `folios` + 费用明细 | 生成时间 | `(hotel_id, stay_id, policy_version)` |
| F9 | 退款成功 | 渠道返回可核实成功 | `refunds` | 渠道确认时间 | `(hotel_id, refund_request_id)` |
| F10 | 房卡签发 / 注销 | 凭证写入或状态变更 | `key_credentials` | 写入时间 | `(hotel_id, credential_id)` |
| F11 | 房态变更 | 房态写入并留有流水 | `room_status_logs` | 变更时间 | `(hotel_id, request_id)` |
| F12 | 政策发布 | 新版本发布且旧版本冻结 | `hotel_policies` | 发布时间 | `(hotel_id, policy_version)` |

**关键约定**

- F7 与 F9 是两条独立事实。**住宿已结束但退款处理中** 是合法状态，不得为了等退款而把客人一直标为在住。
- F2 与 F9 都必须以**支付渠道可核实的结果**为依据，不以本地乐观写入为依据。
- F6 的生效时点是「旧房权限已撤销」而不是「新房权限已写入」。在此之前必须保留安全的原房使用路径。

## 3. 状态清单

### 3.1 直接保留的现有状态机

| 状态机 | 位置 | 说明 |
| --- | --- | --- |
| 订单商业状态 `ORDER_STATUS` | `lib/hotel-core.ts` | 已实现，继续服务订单商业生命周期 |
| 预订状态 `RESERVATION_STATUS` | `lib/hotel-core.ts` | 表示「订了什么」 |
| 房态 `ROOM_STATUS` | `lib/hotel-core.ts` | 保留，但需扩展为五维（见 3.3） |

### 3.2 需要补充的状态

| 状态 | 取值 | 来源事实 |
| --- | --- | --- |
| 住宿状态 `STAY_STATUS` | `PENDING` / `IN_HOUSE` / `ENDED` / `CANCELLED` | F5、F7 |
| 支付状态 `PAYMENT_STATUS` | `REQUESTED` / `AUTHORIZED` / `CAPTURED` / `FAILED` / `UNKNOWN` | F2 |
| 退款状态 `REFUND_STATUS` | `REQUESTED` / `ACCEPTED` / `REFUNDED` / `FAILED` / `UNKNOWN` | F9 |
| 凭证状态 `CREDENTIAL_STATUS` | `ACTIVE` / `SUSPENDED` / `REVOKED` / `EXPIRED` | F10 |
| 结算状态 `FOLIO_STATUS` | `OPEN` / `SETTLING` / `CLOSED` | F8 |

**押金与预授权**：预授权（`AUTHORIZED`）是资金**占用**而非**入账**。解除预授权**不得**记为一笔真实退款。两者必须有不同的事实与不同的报表口径。

### 3.3 房态必须是五维

`ROOM_STATUS` 单值无法表达「已退房但未清洁」这类现实情况。房态应拆成五个可独立判断的维度：

| 维度 | 含义 | 决定方 |
| --- | --- | --- |
| 是否被预订 | 未来某段日期已被占用 | 预订服务 |
| 是否实际在住 | 当前有人住 | 入住服务 |
| 是否清洁完成 | 客房部已完成 | 客房服务 |
| 是否可维护 | 无维修 / 封房 | 工程 |
| 是否可销售 | 以上推导的结果 | 派生 |

**已退房但未清洁的房间不得自动转为可销售。**

## 4. 关键流转规范

### 4.1 身份证入口（入口 A）

放置身份证**不等于**新建一次入住。同一人可能已入住、带同行人、丢卡、订了两间房，或存在多笔不同日期的预订。

```
放置身份证
    │
    ▼
读取证件 + 本人核验
    │
    ▼
查询当前酒店的有效业务记录
    │
    ├── 有待入住预订   → 办理入住
    ├── 已经入住       → 查询房间 / 补卡
    ├── 有多笔预订     → 选择对应预订
    ├── 有历史住宿     → 明确区分「本次」与「上次」
    ├── 无预订         → 现场订房（酒店允许时）
    └── 身份异常       → 停止自动办理，转人工
```

**关系模型要求**：一笔订单可关联多个预订，一个预订可关联多个登记住客（同行人）。**禁止**用姓名或证件号作为订单关系的唯一键。

### 4.2 房卡入口（入口 B）

```
插入房卡
    │
    ▼
验证凭证
    │
    ▼
查询该凭证对应的有效住宿
    │
    ├── 凭证无效 / 已注销        → 提示无效卡，转人工
    ├── 凭证有效但住宿已结束     → 提示「该住宿已结束」，提供开票 / 查询
    ├── 无有效住宿               → 提示无有效住宿，转人工
    └── 找到有效住宿
           │
           ▼
       展示可用服务
           ├── 退房
           ├── 换房
           ├── 房卡异常处理（补卡 / 挂失）
           └── 联系工作人员
```

**必须区分三种「不成功」**：卡无效、卡已注销、卡对应已结束的住宿。三者的处理路径不同，不能合并成一个错误提示。

### 4.3 退房（住宿结束 ≠ 退款完成）

```
退房请求
    │
    ▼
生成结算单（依据适用政策版本 + 实际住宿记录 + 费用明细 + 真实资金流水）
    │
    ▼
展示明细给客人确认
    │
    ▼
成立 F7 住宿结束  ← 此刻即可释放房间，进入清洁流程
    │
    ▼
发起退款（可能先解除预授权）
    │
    ▼
F9 退款成功 / 失败 / 结果未知
```

**硬性要求**：退房服务**不得**直接调用「退总金额」。它只能生成结算单，由账务服务确定可退金额后再发起退款。结算单必须保留计算依据、政策版本、人工调整记录与支付来源。

### 4.4 换房（三阶段，不可合并）

| 阶段 | 内容 | 失败处理 |
| --- | --- | --- |
| 1 准备 | 核验客人、确认新房可用、房价差额、入住条件，**暂时锁定新房** | 释放新房锁，原状态不变 |
| 2 交接 | 写入新房权限并确认可用；按政策保留必要的旧房进入时间以便取行李 | **保留原房有效路径**，不得先退旧房 |
| 3 完成 | 更新正式分配记录、撤销旧房权限、记录原房交接、转保洁/检查状态 | 旧房权限撤销失败则告警并转人工 |

**禁止**：先把旧房退掉，再寄希望于新房卡写入成功。

## 5. 金额定义与结算

| 金额 | 大白话 | 来源 |
| --- | --- | --- |
| 订单应付金额 | 客人原本应该付多少 | `orders` 价格明细 |
| 实际收款 | 支付渠道真正收到了多少 | `payments` |
| 已发生费用 | 已住房晚 + 额外消费 + 适用收费 | 住宿记录 + 消费明细 |
| 应退金额 | 按条款和实际结算后应该返还多少 | **结算单计算得出** |
| 实际退款 | 渠道已经成功退回多少 | `refunds` |

**推算示例**（三晚 × ¥300 + 押金 ¥200，住一晚后提前退房，政策允许未住房晚全额退款）

| 项目 | 金额 |
| --- | --- |
| 已收房费 | ¥900 |
| 实际住宿费 | ¥300 |
| 未住房费退款 | ¥600 |
| 押金返还 | ¥200 |
| **合计待返还** | **¥800** |

**「算出 ¥800」不等于「已退 ¥800」。** 退款请求、渠道受理、最终成功、失败，四个环节分开记录。

**不得使用「总金额 ÷ 晚数」计算**。多晚不同房价、部分不可退、优惠券、税费、延迟退房费、损坏赔偿、人工审核都会破坏这个简化。

## 6. 政策中心

政策按适用范围分五层解析，**这不是可覆盖法律或合同的绝对排序**；条款冲突时按适用法律与合同处理，无法自动判定的交授权人员。

| 层次 | 内容 |
| --- | --- |
| 1 强制要求与合法约束 | 法规、安全、身份登记要求 |
| 2 订单已成立的约定 | 订房时明确适用的取消、退款、价格条款 |
| 3 订单特殊条件 | 房价计划、OTA、协议客户、优惠券、特别约定 |
| 4 酒店通用政策 | 入住/退房时间、押金、服务政策 |
| 5 已授权的例外 | 补偿、减免、特殊退款（保留审批与审计） |

**核心规则**：政策必须有不可变的已发布版本。订单保存**适用版本或条款快照**。管理员可发布新政策，但**不得原地改写旧版本**。

> 客人 9 月 1 日订房，当时允许提前退房退还未住房费；酒店 9 月 10 日改了政策。9 月 1 日那笔订单不得被静默套用新规则。

**发布流程**：AI 生成草稿 → 结构化规则校验 → 模拟典型订单 → 展示受影响范围与退款差异 → 有权限管理员确认 → 发布新版本 → 同步到新订单结算规则、前台政策页、自助终端、AI 知识来源。

AI 不得绕过审批发布涉及资金的政策、改写历史条款或修改支付记录。

## 7. 时间与营业日

**所有业务时间字段同时记录两个值**：UTC 时间戳 + 营业日 `business_date`。

原因：凌晨 1 点退房属于前一个营业日还是当天，直接影响跨日价格、延迟退房费、夜审锁定与历史结算。不能依赖服务器日期。

`business_date` 由酒店的夜审规则决定，不由 `new Date()` 决定。现有 `hotels.business_date` 字段可作为载体。

## 8. 人工接管矩阵

无人化不能阻止客人获得必要的帮助。以下情形必须能暂停、恢复、升级并留审计：

| 情形 | 处理 |
| --- | --- |
| 身份核验异常 / 证件不符 | 停止自动办理，转前台 |
| 无房可换 | 保留原房，提供选项，转前台 |
| 退款争议 | 冻结结算单，转授权人员 |
| 卡片无法注销 | 告警 + 门锁侧挂失，转工程 |
| 支付成功但发卡失败 | 不得显示成功，转前台并保留订单在住 |
| 换房写入中途卡住 | 保留原房路径，转人工 |
| 停电 / 火警 | 安全降级，门锁离线能力接管 |

## 9. 失败与未知结果

**原则：无法确认成功时，不能显示成功。**

| 情形 | 记录 | 对外表现 |
| --- | --- | --- |
| 渠道超时，结果未知 | `UNKNOWN` | 提示处理中，不得重复发起 |
| 读证成功但服务端无响应 | 保留已读事实，不推进状态 | 提示稍后重试或转人工 |
| 付款成功但发卡失败 | 订单在住，房卡未发 | 转前台，不得显示入住完成 |
| 退款请求已提交结果未知 | `UNKNOWN` | 保持「退款处理中」 |

`UNKNOWN` 是一等状态，必须有明确的对账任务负责把它收敛为成功或失败。

## 11. 三个交互入口的职责边界

| 入口 | 触发 | 可做的事 | 不可做的事 |
| --- | --- | --- | --- |
| A 身份证 | 放置证件 | 身份核验、办理入住、补卡、查询本人预订 | 退款、换房、查看他人信息 |
| B 房卡 | 插入房卡 | 识别当前住宿、退房、换房、房卡处理 | 新建订单、查看他人信息 |
| C 前台与后台 | 员工登录 | 订单、房态、政策、财务、异常、人工接管 | 跨酒店操作、改写历史条款 |

**一处修正**：AI 不是入口 C 的专属能力，而是**贯穿三个入口的一层**。自助终端上同样有对话式交互。建议表述为「三个交互面 + 一个贯穿的 AI 层」，否则终端的对话能力在架构上没有归属。

**隐私边界**：一个订单可能有多个客人、多间房。同行人无权查看主预订人的支付信息或申请退款。读卡器不得让下一个人看到上一个人的证件、房号或账单。

## 12. 与阶段划分的依赖修正

产品定义的五阶段（数据可信 / 业务可信 / 规则可信 / 设备可信 / 运营可信）依赖关系需要调整：

**问题**：结算属于「业务可信」（阶段 2），但「应退金额」必须依据政策，而政策中心属于「规则可信」（阶段 3）。若按原顺序，阶段 2 的结算会先写死规则，阶段 3 再重写。

**建议**：把政策中心的**最小可用版本**提前到阶段 2，只包含「条款快照 + 版本不可变 + 按版本结算」三件事；AI 辅助起草、模拟、影响面分析等留在阶段 3。

**另一个建议**：结算与政策的计算逻辑应实现为**纯函数**（不接触数据库），这样可以同时被三处复用：单元测试、后台退款模拟、AI 的「如果现在退房能退多少」问答。这也是把 AI 安全地接入资金环节的前提——AI 调用的是同一个确定性函数。

3. 押金默认采用「实际扣款」还是「预授权」？影响结算单与退款流程设计。
4. 退款是否需要授权人员审批的金额阈值？阈值多少？
5. 夜审时点（默认凌晨几点）与跨日规则由谁配置？
6. 同行人授权模型：谁可以授权、授权存在哪里、退房时是否需注销全部凭证？

## 结论

本规范的作用不是新增文档，而是让后续的数据库、接口、AI 工具与硬件围绕**同一份业务事实**实现。缺少它时，即使 `orders` 已经成功替代 `demo_orders`，矛盾仍会在入住、房态、房卡与财务之间重新出现。

建议执行顺序：**先评审本规范的 13 节与第 13 章待决策项，再据此调整阶段划分，最后才开始写入住、退房、换房、结算的代码。**
