# 第一阶段产品立项及研发任务书：AI 酒店控制台与连接器

## 1. 文档信息

- 产品名称：Hotel Agent OS / AI 酒店控制台
- 阶段：Phase 1，连接现有 PMS 与门店设备
- 文档用途：立项评审、范围确认、研发排期、样板店验收
- 目标客户：已有 PMS 的单体酒店、无人酒店、少人值守酒店
- 首批场景：中国大陆门店，优先广州、珠海等样板店

## 2. 立项背景

酒店通常同时使用 OTA、PMS、门锁、身份证读卡器、公安旅业住宿登记系统、支付、发票、监控和员工沟通工具。系统之间的数据结构和操作入口不同，前台承担大量重复录入、核对和异常处理工作。

第一阶段不替换酒店现有 PMS，而是在现有系统之上建设 AI 控制台、统一事件层和连接器。AI 负责理解目标、查询数据、编排步骤和解释结果；订单、房态、账务、身份登记、支付和发卡仍由确定性业务服务执行。

## 3. 建设目标

### 3.1 业务目标

1. 打通一次完整的无人入住闭环：订单匹配、身份核验、公安登记、PMS 入住确认、门锁凭证生成、退房和保洁派单。
2. 将跨系统查询和日常派单集中到一个 AI 工作台。
3. 让低风险任务自动执行，高风险和不确定任务进入人工确认。
4. 用真实门店数据验证 AI 能减少多少前台操作，并识别第二阶段应自研的 PMS 模块。

### 3.2 技术目标

1. 建立酒店统一数据模型、事件契约、工具契约和连接器规范。
2. 所有外部写操作具备幂等、超时、查询状态、重试、补偿和审计能力。
3. 完整身份证字段、证件照片、人脸特征不进入大模型、RAG、普通日志或跨门店数据区。
4. 公安登记、支付、入住确认和发卡均以真实回执推进状态，不以模型文本或前端提示作为成功依据。

## 4. 非目标

本阶段不建设完整自有 PMS，不承诺替代酒店现有账务、夜审和渠道管理系统；不自动绕过验证码、证书告警或公安系统人工核验；不在未取得酒店、设备厂商、PMS 厂商和属地公安授权的情况下连接生产系统；不让 AI 直接操作数据库、设备 SDK 或浏览器页面。

## 5. 产品范围

### 5.1 AI 酒店控制台

- 今日到店、离店、在住、可售房、脏房和维修房
- 待完成身份核验、公安登记、支付、发卡和清扫任务
- 门锁、读卡器、发卡机、公安 Worker、PMS 连接器健康状态
- 数据冲突、回执未知、长时间未完成工作流和人工接管队列
- 老板日报、前台交接班摘要、房务优先级和异常说明

### 5.2 AI 工作台

支持自然语言和语音查询，例如：

- 今晚还有多少可售房
- 哪些到店客人尚未完成身份核验
- 305 房为什么不能销售
- 将 1208 房列为优先清扫并通知房务
- 解释今天退款和换房异常

查询型工具可直接执行。改价、退款、取消订单、远程开门、修改身份信息等操作必须进入人工确认或专岗处理。

### 5.3 首批 Agent

| Agent | 主要职责 | 自动执行边界 |
| --- | --- | --- |
| Router | 识别意图、紧急程度、风险和负责 Agent | 只做路由，不写业务数据 |
| 客服 Agent | 政策问答、入住说明、投诉收集、转人工 | 只读取脱敏数据，可发送模板消息 |
| 预订 Agent | 查询库存、报价、创建申请、改期申请 | 正式变更由 PMS 工具执行 |
| 房务 Agent | 创建清扫和维修任务、调整优先级 | 不直接将脏房改为可售 |
| 运营 Agent | 经营日报、渠道分析、调价建议 | 第一阶段默认只建议，不自动改价 |

### 5.4 首批连接器

1. PMS：订单、房态、锁房、入住、退房和回执查询。
2. OTA：新订单、取消、改期、库存和价格同步；首批可先接 PMS 聚合后的 OTA 数据。
3. 身份证读卡器：由门店 Windows Worker 封装厂商 SDK。
4. 公安旅业住宿登记：采用属地批准的接口、前置机或受控浏览器 Worker。
5. 门锁和发卡机：写卡、回读、吐卡、取卡检测和命令状态查询。
6. 支付：支付单、异步回调、查询、退款申请和对账。
7. 消息：短信、微信服务通知或酒店现有消息渠道。

## 6. 国内公安旅业系统接入专项

### 6.1 法律和业务基线

项目上线前应由酒店和属地顾问核对现行的旅馆业治安管理、居民身份证、外国人住宿登记、个人信息保护、数据安全和网络安全要求。本任务书只定义产品与工程边界，不替代属地公安机关的接口规范、验收要求和法律意见。

中国大陆各地公安旅业住宿登记系统的产品、接口开放方式、前置机、证书、字段、网络环境和人工核验要求可能不同。项目不得假定存在全国统一公开 API。每个门店上线前必须取得属地接口材料、测试账号或经批准的操作方式。

### 6.2 接入模式

按优先顺序支持三种模式：

1. **官方或授权接口**：通过专线、政务外网、前置机或授权 API 提交并查询回执。
2. **厂商前置机/插件**：由公安认可或酒店现有供应商提供本地服务，Hotel Agent OS 只调用受控本地接口。
3. **受控浏览器 Worker**：在门店专用 Windows 节点运行独立浏览器会话，模拟人员正常操作；遇验证码、证书异常、页面改版或人工核验立即暂停并转人工，不规避安全措施。

禁止使用未经授权的抓包、逆向私有协议、共享他店账号或绕过验证码的方式接入。

### 6.3 数据边界

- 完整证件字段和证件照片仅存在门店受控身份区或经批准的专用存储。
- 云端业务系统只保存短期身份 Token、登记状态、脱敏摘要和公安回执引用。
- AI 上下文只接收“核验通过/失败/需人工”等结果，不接收完整身份证号、住址、照片或人脸模板。
- 身份区、业务区、AI 区、日志区和分析区分开授权。
- 所有调阅、修改、补报、撤销和人工接管操作记录操作者、门店、设备、时间、原因和结果。
- 保存期限、删除、匿名化和备份策略必须按属地要求及酒店制度配置，不能写死为全平台统一值。

### 6.4 公安登记状态机

```text
NOT_STARTED
  -> IDENTITY_READY
  -> SUBMITTING
  -> SUBMITTED
  -> ACKNOWLEDGED
  -> COMPLETED

异常分支：
REJECTED / UNKNOWN / MANUAL_REVIEW / RESUBMIT_REQUIRED
```

只有 `COMPLETED` 且回执可校验时，正常无人入住流程才能继续 PMS 入住确认和发卡。若属地规则允许后补报，必须由门店配置明确的条件、时限、责任人和人工审批，AI 不得自行决定先入住后补报。

### 6.5 断网和异常处理

| 异常 | 系统动作 | 人工动作 |
| --- | --- | --- |
| 公安网络不可达 | 任务保持 `UNKNOWN`，先查询状态，不重复提交 | 通知前台/安全岗，按属地预案处理 |
| 回执丢失 | 使用同一业务幂等标识查询 | 无法确认时人工核对 |
| 验证码或人工核验 | 暂停浏览器 Worker | 由授权员工接管 |
| 页面结构变化 | 熔断自动化，不继续点击 | 更新适配器并重新验收 |
| 证件读取失败 | 最多按设备策略重试 | 使用合法的人工登记路径 |
| 境外人员或特殊证件 | 转专用流程 | 按属地规定登记和报送 |
| 断网期间到店 | 不默认为可入住 | 执行酒店与属地公安批准的离线预案 |

## 7. 目标架构

```text
客人终端 / 管理后台 / 员工工作台
                    |
              AI Router 与 Agent
                    |
            受控工具与工作流服务
                    |
     统一事件、任务、权限、审计与投影
          /         |          \
      PMS适配器   门店设备Worker   公安Worker
        |       读卡/发卡/门锁       |
      外部PMS                      属地旅业系统
```

云端不直接访问 USB、串口、门锁 SDK 或公安页面。门店 Worker 主动建立受认证的出站连接，并按门店隔离证书和密钥。

## 8. 核心工作流

### 8.1 已预订客人入住

```text
订单唯一匹配
-> 身份证放置与读取
-> 人证与订单条件核验
-> PMS 锁房
-> 公安登记并取得回执
-> PMS 确认入住
-> 门锁写卡/密码生成
-> 回读和出卡检测
-> 客人取走证件和房卡
-> 入住完成
```

### 8.2 现场入住

```text
完整手机号确认
-> 创建草稿
-> 后端报价
-> 客人确认
-> 生成支付单
-> 支付回执确认
-> 创建正式订单
-> 进入身份、公安、PMS 和发卡流程
```

### 8.3 退房与清扫

```text
退房请求
-> 查询账务和未结项目
-> PMS 退房确认
-> 注销门锁权限
-> 房间转为待清扫
-> 创建房务任务
-> 清扫与检查完成
-> PMS 房态恢复可售
```

## 9. 数据权威归属

| 事实 | 第一阶段权威来源 | 本地用途 |
| --- | --- | --- |
| 商业订单和金额 | 现有 PMS/支付系统 | 脱敏副本和查询投影 |
| 住宿日期与订单状态 | 现有 PMS | 工作流判断和展示 |
| 房态和库存 | 现有 PMS | 缓存、冲突检测 |
| 支付成功 | 支付服务商回执 | 状态推进和对账 |
| 公安登记成功 | 属地系统回执 | 入住门禁条件 |
| 门锁执行结果 | 门锁控制器回执 | 凭证状态和审计 |
| AI 任务和人工接管 | Hotel Agent OS | 自有任务记录 |

任何字段都必须标明来源、版本、更新时间和可信等级。发生冲突时停止自动写入并创建人工任务。

## 10. 研发工作包

### WP1：统一数据与事件

- 完成订单、房态、入住、身份结果、公安任务、设备命令和人工任务模型。
- 建立事件去重、顺序控制和重放机制。
- 定义跨系统关联 ID：`tenant_id`、`hotel_id`、`case_id`、`command_id`、`idempotency_key`、`trace_id`。

### WP2：连接器框架

- 统一认证、超时、重试、限流、熔断和健康检查。
- 为每个写操作实现状态查询，结果未知时禁止盲目重试。
- 建立测试沙箱、模拟器和录制回放用例。

### WP3：公安与身份 Worker

- 封装读卡器 SDK，输出短期身份 Token 和核验结果。
- 实现三种公安接入模式中的目标门店模式。
- 建立字段映射、回执校验、失败队列、补报和人工接管。
- 完成证书、账号、终端绑定和门店隔离。

### WP4：入住工作流

- 将状态机持久化到 `workflow_runs` / `workflow_steps`。
- 实现暂停、恢复、重试、取消和人工接管。
- 确保公安登记或 PMS 回执缺失时不能发卡。

### WP5：AI 控制台

- AI 查询、任务列表、异常解释和人工确认中心。
- Agent 只能调用 schema 校验后的受控工具。
- 模型不可用时退回规则路由，入住核心流程仍可运行。

### WP6：安全与运维

- 门店和租户隔离、RBAC、密钥轮换、审计和告警。
- 敏感字段脱敏、加密、最小化采集和访问审批。
- 建立门店 Worker 远程升级、回滚和健康监控。

## 11. 里程碑与出口标准

### M0：目标门店与授权确认

- 已确定 PMS、门锁、读卡器、发卡机和公安系统版本。
- 酒店提供合法测试账号、接口材料和设备环境。
- 明确公安数据字段、保存期限、补报规则和人工岗位。

### M1：全仿真闭环

- 所有连接器均使用模拟器。
- 正常、重复、超时、未知和人工接管用例可重放。
- AI 无法绕过状态机。

### M2：单系统真实联调

- PMS 测试环境、读卡器、门锁和公安测试环境分别通过。
- 每个命令具备可查询回执和幂等验证。

### M3：样板店影子运行

- AI 只建议和记录，不自动执行生产写操作。
- 连续运行至少一个完整经营周期，核对订单、房态、身份和任务差异。

### M4：受控自动化

- 低风险任务自动执行，高风险任务必须确认。
- 出现连接器异常时自动熔断并回到人工流程。
- 完成真实门店验收和应急演练。

## 12. 验收指标

- 连续 100 次测试自动入住，无重复公安提交、重复入住和重复发卡。
- 公安登记或回执未知时发卡次数为 0。
- 完整身份证号、证件照片和人脸模板进入模型或普通日志的次数为 0。
- 所有外部命令均可通过 `command_id` 查询最终状态。
- 服务重启后工作流可恢复，不依赖浏览器内存状态。
- 房态冲突、支付未知、公安异常和设备离线均产生人工任务。
- 人工可以看到 AI 的动作、依据、权限、回执和失败原因。

## 13. 团队配置

- 产品负责人：酒店业务、样板店流程和验收
- 后端/领域工程师：工作流、状态机、数据和工具层
- 连接器工程师：PMS、OTA、支付和消息渠道
- Windows/设备工程师：读卡器、发卡机、门锁和公安 Worker
- AI 工程师：Router、Agent、评测和降级策略
- 测试工程师：并发、幂等、故障注入和门店验收
- 安全与合规负责人：公安接入、个人信息和上线审批

## 14. 立项决策门槛

满足以下条件后进入真实接入开发：已选定样板店；已取得 PMS 和设备接口材料；已与属地公安或其指定供应商确认允许的接入模式；酒店确认身份数据处理规则；已指定异常时的人工值守责任人。
